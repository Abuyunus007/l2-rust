## Goal
Add an Accounts view. The **login server's** admin endpoint serves it, because the login server owns the `accounts` table. The supervisor relays it.

1. **Search** accounts by name prefix, 50 per page. Show the login, access level, last active, last server, banned or not, and the last IP on demand.
2. **Create** an account: login, password twice, access level. Use the same rules and hash as the Java login server (SHA-1, Base64, and the login name rules of `LoginController`), and write the same row.
3. **Change, ban or delete:**
   - **Change the password.**
   - **Set the access level.** Show the names from the game server's `AccessLevels.xml` next to the number.
   - **Ban or unban.** Ban sets `accessLevel = -1`, as Java's AccountManager does. Also show what `//ban_acc` writes on the game side.
   - **Delete.** Ask twice. Java's AccountManager deletes the account and the rows of its characters: port exactly what it deletes, or leave delete out and say so in the report.
4. Java's `AccountManager` tool is the spec for what each action writes.

## Requirements
- Passwords are never logged and never sent back. The GUI drops them after the request.
- DB tests run only with `L2_TEST_DATABASE_URL`. Everything else uses the in-memory store the login tests use.

## Tests
- Each action against the store:
  - create: the hash equals the Java vector in `java-vectors/out`;
  - ban and unban;
  - access level;
  - search paging.
- The admin endpoint round trip (port 0).

## Goal
Fix what M7-E2E-01 found, then un-ignore its test:
1. **Flag Display cannot take a fortress.** (a) `Condition::PlayerCanTakeFort` is not modelled (`stats/conditions.rs`, grouped with `NotModelled::CanAction`): port Java's `ConditionPlayerCanTakeFort`. (b) The cast's launch/escape-range check in `skills/cast.rs` drops non-creature targets (the flag pole is a static object) and aborts silently, so `TakeFort` never runs. Read how Java's `FlagPole` target handler, `Skill.getTargetList`, `Creature.onMagicLaunchedTimer` and `TakeFort` handle the pole and make the Rust path reach `TakeFort` the way retail does (if Java itself would hit a null there, port the behaviour that lets the fortress be taken on a stock server and mark it `NOTE(java-quirk)`). Un-ignore `fort::flag_display_takes_the_fortress` in `e2e/m7_fort.rs` (`Finish::Skill`, `flag_condition: true`).
2. **Function rows of a residence owned only in this world.** With `SiegeDatabaseWrites` off, a GM test siege or `//clanhallset` gives a residence an owner in this world only (the owner row is a Job write, not written), but buying a function afterwards is a Player write and lands a `clanhall_functions`/`castle_functions` row for a residence the DB thinks is free. Track on each residence whether its current owner came from the database (startup or a D-50 re-read) or only from this world; function writes (buy, change, remove, fee) for an owner that exists only in this world are not written, like the other D-51 jobs. Adjust the assertion in `e2e/m7_hall.rs` accordingly.
